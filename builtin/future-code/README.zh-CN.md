# future-code 中文说明

`future-code` 是 FutureOS 的轻量代码开发技能。FutureOS 是面向广泛用户的综合 Agent，
因此代码开发以技能形式按需加载，不作为所有任务的默认人格或固定工作流。

## 触发定位

当前工作目录位于 Git 仓库中，并且用户的请求涉及源代码、测试、构建、配置、调试、
重构或代码审查时，应优先考虑加载本技能。Git 仓库是强触发信号，但不是唯一条件：
仓库里的写作、资料整理等非代码任务仍由 Agent 根据任务本身判断；仓库外明确的代码
开发任务也可以使用本技能。

## 英文技能全文翻译

### 轻量代码开发

帮助用户完成软件工作，不预设用户具有开发背景。把用户想要的结果转化为仓库内的
具体工作，以通俗语言说明关键决策，并让工作流程与任务规模相匹配。

### 1. 明确范围与仓库上下文

1. 判断当前目录是否属于 Git 仓库。当请求涉及代码、测试、构建、配置、调试、重构
   或审查时，把 Git 仓库视为强选择信号。仅仅位于仓库中，不代表无关任务也属于代码开发。
   Git 可用时，通过 `git rev-parse --show-toplevel` 定位仓库根目录，并用
   `git status --short --branch` 记录初始状态。
2. 在决定工作方式前读取适用的指令。检查仓库根目录及相关父目录、子目录中的
   `AGENTS.md`、`CLAUDE.md`、README 和贡献指南。更具体的仓库指令优先于本通用流程。
3. 判断用户需要的是解释、调查、实现还是审查。保持用户明确划定的边界：诊断本身不
   授权修复，审查本身也不授权编辑，除非用户同时要求修改。

### 2. 修改前先理解

编辑前，先形成足够的工作理解，至少弄清楚：

- 行为实际由哪里负责；
- 它如何被调用和使用；
- 哪些测试、配置、文档或外部契约定义了预期行为；
- 相关文件中是否包含用户已有修改。

调查深度应与任务规模和风险相匹配，但不要根据一条孤立的搜索结果或假定的惯例直接修改。
搜索是建立理解的方法，不能代替结合上下文阅读相关代码。

在本地分阶段探索，不要一开始就广泛读取整个仓库：

1. 使用 `rg --files` 列出候选文件，通过 `-g` 模式或目录参数缩小范围。使用 `rg -n`
   搜索文本和符号，仅在需要周边行时添加 `-C`。ripgrep 可用于 Windows、macOS 和 Linux。
2. `rg` 不可用时，对已跟踪内容使用 `git grep -n`，再使用当前平台已有的原生工具，
   例如 PowerShell 的 `Get-ChildItem` 或 `Select-String`。小任务已有合适替代方案时，不要
   仅为搜索而安装新工具。
3. 默认遵守忽略规则。只有任务需要时才扩展到被忽略或生成的路径；避免用宽泛的
   `rg -uu` 扫描依赖和构建输出。
4. ripgrep 退出码 1 表示“没有匹配”，不是工具故障。断定符号或文件不存在前，检查命令
   和搜索范围是否正确。
5. 从文件名和符号逐步进入实际负责实现、调用位置、测试和配置。阅读足够的局部上下文，
   包括导入、类型和相邻逻辑，避免根据孤立行修改代码。

当前工具支持时，可以并行执行互不依赖的搜索和读取；存在依赖关系的步骤保持顺序执行。
遵循现有架构、命名、类型、依赖和生成文件边界。原因不确定时，区分已确认事实和待验证
假设；只有会实质改变结果的选择才询问用户。

当前代码无法解释设计决定时，有针对性地查看历史：

```text
git log -- path/to/file
git log -S 'literal or symbol'
git log -G 'pattern'
git blame -L START,END path/to/file
```

用历史回答具体问题，不把历史扫描变成每次修改的固定步骤。

### 3. 实施聚焦的修改

- 实现满足请求所需的最小完整改动。避免无关清理、推测式抽象、新增依赖和大范围重写。
- 保护用户已有工作。仔细检查重叠修改，不回退无关变更；无法安全整合时停止并说明情况。
- 聚焦修改使用精确编辑；真正机械化的批量修改使用合适的批处理方式。两种情况都要检查
  实际 diff。
- 优先使用项目已有机制并修改事实来源文件。仓库提供生成器时，不直接手改生成结果，
  而是运行项目记录的生成命令。
- 当行为、回归风险或复杂逻辑需要长期保障时，新增或更新测试。不要编写只重复静态值或
  照抄实现逻辑的测试。

### 4. 按比例验证

从仓库指令、清单、脚本和 CI 中确定验证命令，不假设某一种包管理器或构建系统。考虑
当前 shell 和平台，包括项目提供的 `.sh`、`.ps1` 和 `.cmd` 入口。先运行最贴近改动范围
的检查，仅在改动性质或仓库规则要求时扩大范围。适用检查可以包括测试、构建、类型检查、
lint、格式化和快照。

只有实际成功运行的检查才能报告为通过。说明跳过或受阻的检查及其实际影响。当现有工具
无法实际运行某项行为时，尽可能使用其他相关证据，并给用户一个简短、具体的人工检查步骤；
不得把间接证据描述成运行时验证。让不同验证的结果可以单独判断：不要让后续“无匹配”的
搜索或被忽略的退出码掩盖前面格式化、构建或测试的结果。保留真实错误，重试前先判断问题
来自代码改动、环境、缺少依赖还是权限。

### 5. 保持 Git 工作可见且可恢复

- 默认在当前 checkout 中工作。如果用户、仓库指令或交付流程要求分支或独立 checkout，
  应清楚说明其位置和最终 Git 状态。
- 交付前使用 `git diff --stat` 检查范围，使用 `git diff` 检查内容，并使用
  `git diff --check` 查找空白错误。同时查看 `git status --short --branch`，因为普通 diff
  不会显示未跟踪文件的内容。排除意外文件、生成噪声、密钥和无关修改。
- 只有当前请求或既定流程授权时，才提交、推送、创建 PR、合并或发布。报告实际结果，
  不把计划中的结果当成已完成。

### 6. 有意识地升级长任务

需要跨会话继续、运行较长时间、维护持久 todo，或用户明确要求“继续工作”时，使用
`future-loop`。创建前检查是否已有匹配目标，定义具体完成证据；普通一次性修改留在当前
会话中完成。

### 7. 遵守工具边界并清楚交付

只使用当前会话实际提供的工具。安全引用路径，尤其是包含空格的路径；根据当前 shell 选择
语法，不根据操作系统名称猜测。如果委派能力可用且适合任务，只分配边界清楚的代码或证据
任务；主 Agent 仍负责最终整合，并独立验证委派结果。

结束时说明结果、重要文件或行为变化、已经执行的验证，以及剩余限制或人工检查。简单任务
保持简短；较大改动提供足够信息，让用户能够判断风险。

## 内容分类

| 分类 | 作用 |
|---|---|
| 需求与范围 | 区分解释、调查、实现和审查，保持用户授权边界 |
| 代码理解 | 快速搜索文件和符号，读取仓库指令、实现、调用关系、配置、测试和必要历史 |
| 修改原则 | 保持现有架构与风格，实施最小完整改动并保护已有工作 |
| 工具与执行 | 使用当前可用工具和项目真实命令，不假设特定技术栈 |
| 验证与自查 | 按风险运行针对性检查，检查最终 diff，准确报告验证边界 |
| 长任务推进 | 将跨会话或持续任务交给 `future-loop`，普通任务直接完成 |
| 沟通与交付 | 用用户能理解的语言说明结果、验证、风险和必要人工步骤 |

## 技能修改约束

1. 保持触发描述准确。Git 仓库应提高选择优先级，但不能让技能吞掉仓库中的科研、写作、
   数据检索等非代码任务。
2. 保持轻量。不要复制通用 Agent 提示词，不绑定具体语言、框架、包管理器或 CI 平台；
   项目专属规则继续由仓库指令负责。
3. 不把当前客户端或工具集的暂时性能力差异固化进技能。运行时只使用会话实际提供的工具，
   缺少关键验证能力时准确说明边界。
4. 保持技能边界。一次性开发由本技能负责，持久长任务复用 `future-loop`，不要在本技能
   中复制 loop 的控制面命令和状态协议。
5. 保持授权语义。技能帮助执行用户要求的开发工作，不把调查、审查或仓库存在本身扩展为
   修改、提交、推送、建 PR、合并或发布授权。
6. 修改英文入口时同步本翻译和 `skills.json`。行为变化需增加语义化版本号，并运行 builtin
   结构校验及受影响测试。

## 迭代计划

- `0.2.x`：观察真实触发是否过宽或过窄，以及普通开发任务能否稳定完成“理解、修改、验证、
  交付”闭环，只针对已出现的问题做小幅修正。
- 后续仅在真实任务反复暴露同一种工具或验证缺口时，增加相应的条件指引。
- 只有出现重复且容易出错的确定性操作时才增加脚本；只有正文确实过长且属于条件内容时才增加
  references，避免把轻量技能扩成开发手册。
