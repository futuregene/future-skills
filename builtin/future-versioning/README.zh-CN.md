# future-versioning 中文说明

`future-versioning` 是 FutureOS 的轻量版本化开发技能：凡是产出需要纳入 Git 版本管理的
工作，都算它的范围——代码、文档、数据、分析、配置。FutureOS 是面向广泛用户的综合 Agent，
因此这类工作以技能形式按需加载，不作为所有任务的默认人格或固定工作流。

## 触发定位

当前工作目录位于 Git 仓库中，且请求会产生值得跟踪的文件（源代码、测试、构建、配置、
正文文档、数据、图表、分析），或涉及调试、重构、审查、修订这些文件时，应优先考虑加载
本技能。Git 仓库是强触发信号，但不是唯一条件：一次性提问、检索或调研若不产出需要
跟踪的成果，就不属于本流程；反过来，仓库外的工作如果会产出需要版本管理的成果，
也应当使用本技能——并建议用户先建立仓库。

## 英文技能全文翻译

### 轻量版本化开发

帮助用户完成应当纳入 Git 跟踪的工作，不预设用户具有开发背景。成果可以是代码、文档、
数据集、分析或配置：判断它属于本技能的标准是“成果应当进仓库、且其历史有意义”。把用户
想要的结果转化为仓库内的具体工作，以通俗语言说明关键决策，并让工作流程与任务规模相匹配。

### 1. 明确范围与仓库上下文

1. 判断当前目录是否属于 Git 仓库。当请求会产出值得跟踪的文件——源代码、测试、构建、
   配置、正文文档、数据、图表、分析——或涉及调试、重构、审查、修订这些文件时，把 Git
   仓库视为强选择信号。仅仅位于仓库中，不代表无关任务也属于本流程：不产出受跟踪成果的
   一次性提问、检索或调研不是。Git 可用时，通过 `git rev-parse --show-toplevel` 定位仓库
   根目录，并用 `git status --short --branch` 记录初始状态。
2. 当工作会产出值得跟踪的成果、但当前还没有仓库时，建议为它建立仓库并说明理由：版本
   历史、可审查的 diff、以及日后能复现或回退到某个状态。可以给出一个朴素的 `git init`
   （再配一个 `.gitignore` 挡住生成物和大文件）；如果用户已有惯用的工具或远端仓库，
   就按用户的选择。只在用户同意后初始化——不要未经询问就把一个普通目录变成仓库。
3. 在决定工作方式前读取适用的指令。检查仓库根目录及相关父目录、子目录中的
   `AGENTS.md`、`CLAUDE.md`、README 和贡献指南。更具体的仓库指令优先于本通用流程。
4. 判断用户需要的是解释、调查、实现还是审查。保持用户明确划定的边界：诊断本身不
   授权修复，审查本身也不授权编辑，除非用户同时要求修改。
5. 让工作在 Git 中留下记录。只要请求的工作修改了受跟踪文件，就提交它：宁要多个小而
   完整的提交，不要最后一次性倾倒；每个提交只做一件事，提交信息要让日后的读者知道
   改动为何存在，而不只是改了什么。不碰无关的未完成修改。提交才使成果可追溯、可复现，
   因此改完却不提交应视为尚未完成——除非用户自己在维护历史并要求不提交。

### 2. 修改前先理解

编辑前，先形成足够的工作理解，至少弄清楚：

- 行为、内容或数据实际由哪里负责；
- 它如何被调用和使用，或有哪些其他文件与文档依赖它；
- 哪些测试、配置、文档或外部契约定义了预期结果；
- 相关文件中是否包含用户已有修改。

调查深度应与任务规模和风险相匹配，但不要根据一条孤立的搜索结果或假定的惯例直接修改。
搜索是建立理解的方法，不能代替结合上下文阅读相关代码。

在本地分阶段探索，不要一开始就广泛读取整个仓库：

1. 使用 `rg --files` 列出候选文件，通过 `-g` 模式或目录参数缩小范围。使用 `rg -n`
   搜索文本和符号，仅在需要周边行时添加 `-C`。ripgrep 可用于 Windows、macOS 和 Linux。
2. `rg` 不可用时，对已跟踪内容使用 `git grep -n`，再使用当前平台已有的原生工具，
   例如 PowerShell 的 `Get-ChildItem` 或 `Select-String`。小任务已有合适替代方案时，不要
   仅为搜索而安装新工具。
3. 默认遵守忽略规则。只有任务需要时才扩展到被忽略或生成的路径；避免用宽泛的
   `rg -uu` 扫描依赖和构建输出。
4. ripgrep 退出码 1 表示“没有匹配”，不是工具故障。断定符号或文件不存在前，检查命令
   和搜索范围是否正确。
5. 从文件名和符号逐步进入实际负责实现、调用位置、测试和配置。阅读足够的局部上下文，
   包括导入、类型和相邻逻辑，避免根据孤立行修改代码。

当前工具支持时，可以并行执行互不依赖的搜索和读取；存在依赖关系的步骤保持顺序执行。
遵循现有架构、命名、类型、依赖和生成文件边界。原因不确定时，区分已确认事实和待验证
假设；只有会实质改变结果的选择才询问用户。

当前代码无法解释设计决定时，有针对性地查看历史：

```text
git log -- path/to/file
git log -S 'literal or symbol'
git log -G 'pattern'
git blame -L START,END path/to/file
```

用历史回答具体问题，不把历史扫描变成每次修改的固定步骤。

### 3. 实施聚焦的修改

- 实现满足请求所需的最小完整改动。避免无关清理、推测式抽象、新增依赖和大范围重写。
- 保护用户已有工作。仔细检查重叠修改，不回退无关变更；无法安全整合时停止并说明情况。
- 聚焦修改使用精确编辑；真正机械化的批量修改使用合适的批处理方式。两种情况都要检查
  实际 diff。
- 优先使用项目已有机制并修改事实来源文件。仓库提供生成器时，不直接手改生成结果，
  而是运行项目记录的生成命令。
- 当行为、回归风险或复杂逻辑需要长期保障时，新增或更新测试。不要编写只重复静态值或
  照抄实现逻辑的测试。成果不是代码时，给它等价的保障——一个检查脚本、一段脚本或一份
  记录在案的人工核验步骤——并与成果一起存入仓库。

### 4. 按比例验证

从仓库指令、清单、脚本和 CI 中确定验证命令，不假设某一种包管理器或构建系统。考虑
当前 shell 和平台，包括项目提供的 `.sh`、`.ps1` 和 `.cmd` 入口。先运行最贴近改动范围
的检查，仅在改动性质或仓库规则要求时扩大范围。适用检查可以包括测试、构建、类型检查、
lint、格式化和快照。

只有实际成功运行的检查才能报告为通过。说明跳过或受阻的检查及其实际影响。当现有工具
无法实际运行某项行为时，尽可能使用其他相关证据，并给用户一个简短、具体的人工检查步骤；
不得把间接证据描述成运行时验证。让不同验证的结果可以单独判断：不要让后续“无匹配”的
搜索或被忽略的退出码掩盖前面格式化、构建或测试的结果。保留真实错误，重试前先判断问题
来自代码改动、环境、缺少依赖还是权限。

### 5. 保持 Git 工作可见且可恢复

这些规则适用于任何受跟踪的成果——代码、正文、数据或配置——因为仓库就是工作的记录。

#### 优先使用工作树（worktree）

除了琐碎的小改动，都把改动放到仓库 `.worktrees/` 目录下的独立工作树中，并使用与改动
匹配的分支。这样多个会话可以同时在同一仓库里工作而不争抢同一份 checkout，共享的只有
基准分支。采用这套默认做法的仓库按此执行；仓库指令另有要求时、或只是一次只读调查时，
直接留在当前 checkout 中。

1. 从远端最新提交分叉，而不是从一个可能落后的本地基准分支分叉：先 `git fetch origin`，
   再 `git worktree add --no-track .worktrees/<name> -b <type>/<name> origin/<base>`。
   `--no-track` 很关键：少了它，普通的 `git push` 会直接推到基准分支。`<type>` 取与改动
   性质匹配的类型（`feat`、`fix`、`docs`、`refactor`、`perf`、`test`、`ci`、`chore`）。
2. 让 `.worktrees/` 保持不被版本控制（没有就加进 `.gitignore`）：它存放的是整份工作副本，
   不是源码。
3. 在工作树内创建、编辑、验证和提交。不要提交到基准分支，也不要把工作树分支合进本地
   基准分支。squash 合并的 PR 会让同样内容得到不同的提交号，于是本地快进会制造分叉，
   之后每次更新基准分支都会被它挡住。
4. 推送前要重新同步，而不只是开头同步一次：再次 fetch，把基准分支合进工作树分支，
   重跑受这次合并影响的检查，然后再推送。落后的分支会在“更新分支”要求和 CI 重排队之间
   反复摇摆。
5. 改动落地后，在同一个会话里收尾：`git worktree remove .worktrees/<name>`、删除本地和
   远端分支、`git worktree prune`，再从远端快进本地基准分支
   （`git fetch origin && git merge --ff-only origin/<base>`）。残留物会把过期的工作树、
   过期的分支或过期的基准分支留给下一个会话。
6. 不要动其他会话的工作：绝不删除、重置或强推不是自己创建的工作树或分支。如果本地
   基准分支上带着不是自己提交的 commit，查明它们属于哪个分支并报告，不要擅自清理。

当仓库或用户要求不同的流程，或本次只是只读调查时，改为直接在当前 checkout 中工作。
仓库指令和用户要求优先于这里的默认做法。

#### 把流程记录下来

仓库指令（`AGENTS.md`、`CLAUDE.md`、贡献指南）才是并行会话真正共享的东西，所以按本技能
工作的仓库应当在那里记录它的交付流程。当仓库还没有记录交付流程时——没有分支或工作树规则、
没有提交或审查期望——直接把该有的那份写下来，单独放在一个提交里，并在交付时连同提交号一起
说明，让用户一步就能撤掉。记录流程属于本次工作本身：一个等回答的提议最容易被跳过，而真正
需要那份文件的下一个会话就什么也读不到。只写符合仓库做法的那部分，并走同样的工作树与审查
流程。如果文件已存在，就补上缺的部分，不要重构别人的文件，并把这些补充单独放在一个提交里。

以下情况先问再写：

- 仓库不是用户说了算的——上游或第三方项目的克隆、改动要回流成 PR、有自己维护者的共享仓库：
  说明要加什么，由维护者决定；
- 仓库已经记录了与本流程冲突的交付方式：按写着的做，只有用户要求时才提议修改；
- 用户说过不希望在这个仓库里写指令文件，或者这只是一次用完即弃的实验，不会交给后续会话。

初始化仓库仍然保留它自己的门槛（见第 1 节）：往已有仓库里写指令是常规且可撤销的，把一个
普通目录变成仓库不是。

**在文件里点名本技能。** 后来打开这个仓库的会话读得到它的指令，却读不到写下这些指令的那次
对话；文件里若没有这句话，就没有任何东西提示它加载本技能。把这句话放在所记录流程的开头，按
仓库情况措辞：

> 本仓库遵循 `future-versioning` 技能，改动受跟踪文件之前先加载它。

这句话让文件从“说明”变成“可执行”：仓库文件记录它自己的决定，步骤、命令和失败处理由本技能
提供。技能名要写准，指针放在会话最先读到的位置，并且不要在其下复述本技能的指令——技能一改，
抄本就成了过期的第二份来源。

**按本技能的形状来写。** 只写会话真正需要的部分，按它需要的顺序，且只写仓库自己决定的内容：

- 范围——仓库装什么，哪些是生成、内嵌或排除的；
- 基准分支，以及改动分支与工作树怎么切、怎么命名；
- 提交期望——粒度、信息格式、提交必须包含什么；
- 交付前的检查关卡：确切的命令，按执行顺序；
- 工作怎么收尾——合并还是 PR、由谁开或合并、之后清理什么；
- 容易出错的边界：不能碰的文件、其他会话的分支、密钥。

不要写不属于仓库指令文件的内容：本技能的默认做法（随工具升级会变，抄一份到这里就成了过期
副本）、会变的现状（开着的 PR、当前任务）、本机路径与凭据，以及工具已经强制的东西。保持一口
气能读完——长成手册的文件没人照着做；长流程给链接而不是内联；新规则优先并进已有小节，而不是
每次追加一节。

**检查它能不能被照着做。** 用一个只有这份文件的会话的眼光重读一遍：它应当能切分支、跑检查、
把工作收尾，而不需要回来问“这里是什么意思”。

#### 交付前自查

- 说明改动在哪里——工作树路径与分支名——以及事后基准分支处于什么状态，方便用户找到并
  试跑。
- 交付前使用 `git diff --stat` 检查范围，使用 `git diff` 检查内容，并使用
  `git diff --check` 查找空白错误。同时查看 `git status --short --branch`，因为普通 diff
  不会显示未跟踪文件的内容。排除意外文件、生成噪声、密钥和无关修改，并确认该提交的
  工作已经提交，而不是留在工作区里。
- 提交你被要求完成的工作；这个本地提交就是可追溯、可审查的记录。推送、开 PR、合并或
  发布则属于更进一步的步骤，只有当前请求或既定流程授权时才做；报告实际结果，不把计划
  中的结果当成已完成。
- 如果本次用到了本技能的流程、而仓库仍然没有记录交付流程，就在交付说明里用一句话点出
  原因。明确说出的缺口是一个决定，没提的缺口读起来就是被跳过的一步。

### 6. 有意识地升级长任务

需要跨会话继续、运行较长时间、维护持久 todo，或用户明确要求“继续工作”时，使用
`future-goal`。创建前检查是否已有匹配目标，定义具体完成证据；普通一次性修改留在当前
会话中完成。

### 7. 遵守工具边界并清楚交付

只使用当前会话实际提供的工具。安全引用路径，尤其是包含空格的路径；根据当前 shell 选择
语法，不根据操作系统名称猜测。如果委派能力可用且适合任务，只分配边界清楚的代码或证据
任务；主 Agent 仍负责最终整合，并独立验证委派结果。

结束时说明结果、重要文件或行为变化、工作记录在哪里（分支，以及相应的提交或 PR）、
已经执行的验证，以及剩余限制或人工检查。简单任务保持简短；较大改动提供足够信息，
让用户能够判断风险。

## 内容分类

| 分类 | 作用 |
|---|---|
| 需求与范围 | 区分解释、调查、实现和审查，保持用户授权边界 |
| 仓库与记录 | 判断成果是否需要版本管理，缺失时建议建仓，并把工作按意图提交进 Git |
| 内容理解 | 快速搜索文件和符号，读取仓库指令、实现、调用关系、配置、测试和必要历史 |
| 修改原则 | 保持现有架构与风格，实施最小完整改动并保护已有工作 |
| 工具与执行 | 使用当前可用工具和项目真实命令，不假设特定技术栈 |
| 交付与并行协作 | 修改放进 `.worktrees/` 独立工作树，基点先更新、推送前再同步、落地后清理并快进基准分支 |
| 验证与自查 | 按风险运行针对性检查，检查最终 diff，准确报告验证边界 |
| 长任务推进 | 将跨会话或持续任务交给 `future-goal`，普通任务直接完成 |
| 沟通与交付 | 用用户能理解的语言说明结果、验证、风险和必要人工步骤 |

## 技能修改约束

1. 保持触发描述准确。产出值得跟踪的成果（代码、文档、数据、分析）就应提高选择优先级，
   但不能让技能吞掉不产出受跟踪成果的一次性检索或问答。
2. 保持轻量。不要复制通用 Agent 提示词，不绑定具体语言、框架、包管理器或 CI 平台；
   项目专属规则继续由仓库指令负责。
3. 不把当前客户端或工具集的暂时性能力差异固化进技能。运行时只使用会话实际提供的工具，
   缺少关键验证能力时准确说明边界。
4. 保持技能边界。一次性工作由本技能负责，持久长任务复用 `future-goal`，不要在本技能
   中复制 goal 控制面的命令和状态协议。
5. 保持授权语义。技能帮助执行用户要求的开发工作，不把调查、审查或仓库存在本身扩展为
   修改、提交、推送、建 PR、合并或发布授权；建立仓库仍要先征得用户同意。唯一默认向前的一步
   是把交付流程记进仓库自己的 `AGENTS.md` / `CLAUDE.md`：它和本次改动走同一个工作树与审查
   流程、单独成一次提交，交付时点名提交号，用户一步即可撤掉；仓库不由用户说了算、仓库已有
   冲突做法或用户明确拒绝时，回到先问。
6. 修改英文入口时同步本翻译和 `skills.json`。行为变化需增加语义化版本号，并运行 builtin
   结构校验及受影响测试。

## 迭代计划

- 当前重点是观察触发是否过宽或过窄：需要版本管理的成果应当稳定命中，不产出受跟踪成果的
  一次性检索、问答不应当命中。只针对已出现的问题做小幅修正。
