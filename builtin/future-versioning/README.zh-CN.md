# future-versioning 中文说明

`future-versioning` 是 FutureOS 的轻量版本化开发技能：凡是产出需要纳入 Git 版本管理的
工作，都算它的范围——代码、文档、数据、分析、配置。它以技能形式按需加载，不作为所有
任务的默认流程。

> 本文件是中文导读，规则以同目录的 `SKILL.md` 为准；两者冲突时按 `SKILL.md` 执行。

## 两个核心目的

技能里的所有规则都服务于两件事：

1. **可追溯的历史。** 任何小的、完整的改动都尽早提交进 Git。日后要回答“什么时间点做了
   什么样的改动、为什么”时，靠的是提交记录；改完不提交，等于没有留下记录。
2. **并发推进一个项目。** 当一个仓库里有多个会话同时工作时，每个改动使用独立的工作树
   和分支，文件不会互相踩踏，只有基准分支是共享的。

仓库自己的指令（`AGENTS.md`、`CLAUDE.md`、贡献指南）比本技能更具体，冲突时以仓库为准。

## 快速路径

1. `git rev-parse --show-toplevel` 与 `git status --short --branch`：我在哪、哪些文件已有改动。
2. 先读仓库指令再决定做法；可能有其他会话时，看 `git worktree list` 和
   `git branch --show-current`。
3. 仓库没有另行规定时做隔离：
   `git fetch origin && git worktree add --no-track .worktrees/<name> -b <type>/<name> origin/<base>`；
   没有 remote 时从本地基准分支创建：`git worktree add --no-track .worktrees/<name> -b <type>/<name> <base>`。
   单 checkout + 声明写域的仓库留在原地。
4. 小步修改，用仓库自己的命令验证，按路径暂存，每一步单独提交，提交信息说明“为什么”。
5. 用 `git diff --stat`、`git diff`、`git status --short --branch` 复核；只有请求或仓库惯例
   授权时才 push、开 PR 或合并。
6. 按「收尾」一节做带守卫的清理：确认改动已落地后再删分支，更新基准分支要在持有它的
   checkout 里做。

## 1. 明确范围

1. “当前目录是 Git 仓库，且任务会产出值得跟踪的文件”——源码、测试、构建、配置、正文、
   数据、图表、分析，以及调试、重构、修订它们——是本技能的选择信号。仅仅位于仓库中，
   不代表只读问答、检索或审查也要走这套流程；审查只有在会改动受跟踪文件时才加载。
2. 会产出成果但还没有仓库时，建议 `git init` 并配 `.gitignore`，说明理由（历史、可审查
   的 diff、可复现可回退），经用户同意后再初始化。不要把普通目录未经询问变成仓库，
   也不要在临时聊天/草稿 workspace 里初始化（见「草稿工作区」）。
3. 先读适用指令。更具体的仓库指令优先，包括它的 worktree 默认做法。
4. 判断用户要的是解释、调查、实现还是审查。诊断不授权修复，审查不授权编辑。
5. 工作过程中持续提交（见「边做边提交」）。改完却不提交的成果视为尚未完成。

## 2. 修改前先理解

弄清行为/内容由谁负责、如何被使用、哪些测试和契约定义预期结果、相关文件是否已有别人的
改动。深度随风险调整，但不要凭一条孤立搜索结果或想当然的惯例下手。

分阶段探索：`rg --files`、`rg -n`（必要时 `-C`）；没有 `rg` 时用 `git grep -n` 或平台
原生工具；遵守忽略规则；退出码 1 是“没有匹配”而不是故障；从名字走到实现、调用点、
测试和配置。能并行就读并行。原因不清时区分事实与假设，只问会改变结果的选择。

需要时用 `git log -- <path>`、`git log -S`、`git log -G`、`git blame -L` 回答具体问题，
而不是每次都扫历史。

## 3. 实施聚焦的修改

- 只做满足请求的最小完整改动，不做无关清理、推测式抽象或新增依赖。
- 保护用户已有工作，不回退无关改动；无法安全整合就停下说明。
- 精确编辑为主，真正机械的批量修改才用批处理；两种都检查 diff。
- 改事实来源文件，生成物用项目生成器，不手改。
- 需要长期保障时补测试；成果不是代码时，补等价保障（检查脚本或成文的人工核验步骤），
  并与成果一起入库。

## 4. 按比例验证

从仓库指令、清单、脚本和 CI 里找命令，不假设包管理器；考虑 shell 与平台差异（`.sh`、
`.ps1`、`.cmd`）。先跑最贴近改动的检查，再按需扩大。

没成功跑过的检查不许说通过；跳过或被阻塞的检查要说明影响，并给一条具体的人工验证。
不把间接证据说成运行时验证；结果要可归因，别让后续的“无匹配”或吞掉的退出码掩盖前面
的格式、构建或测试结果。重试前先判断失败来自改动、环境、缺依赖还是权限。

## 5. 历史与并发

### 边做边提交

- 多个小而完整的提交，优于最后一次性倾倒；一个提交一个意图。
- 提交信息写给日后的读者：为什么改，而不只是改了什么。
- checkout 里可能有别的会话时，按路径暂存（`git add <path>`），不要盲目 `git add -A`，
  也不要动无关的未完成修改。
- 提交你被要求做的改动；push、开 PR、合并只在请求或仓库惯例授权时进行。

### 两种隔离方式

**每次改动一个 worktree（默认）。** 除琐碎改动外，把改动放到 `.worktrees/<name>` 的独立
分支上，多个会话可以同时推进，只有基准分支共享。

1. 从远端最新基点开分支：`git fetch origin`，再
   `git worktree add --no-track .worktrees/<name> -b <type>/<name> origin/<base>`。
   `--no-track` 很重要：否则直接 `git push` 会推到基准分支。类型用 `feat`、`fix`、`docs`、
   `refactor`、`perf`、`test`、`ci`、`chore`。
2. 没有 `origin` 时从本地基准分支开：`git worktree add --no-track .worktrees/<name> -b <type>/<name> <base>`，
   并跳过所有 fetch、push 和删远端分支的步骤。
3. `.worktrees/` 保持不被跟踪（没有就加进 `.gitignore`）。
4. 不要在 worktree 里 checkout 基准分支，那会把它锁给这个 worktree，其他会话就用不了。
   已经在 worktree 里时就在原地工作，不要嵌套（比较 `git rev-parse --show-toplevel` 与
   `--git-common-dir`）。

**单 checkout + 声明写域（仓库这样规定时）。** 有些仓库让多个会话或 goal worker 共用一个
checkout，用声明好的、互不重叠的写域和守卫（例如 `future goal ...`）串行。按它的规矩做：
只提交自己写域内的路径，按名字暂存，不动别人进行中的路径。不要给明确不要 worktree 的
仓库硬加 worktree——独立 checkout 会让守卫和产物引用的路径分叉。

只读调查留在当前 checkout，两种隔离都不建。

### 保持基准分支最新

push 前重新同步：fetch，把基准分支合进改动分支，重跑受影响的检查。落后的分支会在
“update branch”和重跑 CI 之间来回打转。

本地基准分支只在持有它的 checkout 里更新；被别的 worktree 占用时，在那个 worktree 里更新
（没被 checkout 时可用 `git fetch origin <base>:<base>`），绝不从正在运行的会话脚下抽走。
仓库把某个分支当作长期集成分支时，不按本技能的默认去快进它。

### 记录仓库约定

仓库指令是并发会话真正共享的东西。遵循本技能的仓库应该在 `AGENTS.md` 或 `CLAUDE.md` 里
记录自己的交付约定，并点名本技能：

> This repository follows the `future-versioning` skill. Load it before changing tracked files.

这一行让文件变成可执行的入口：仓库记录自己的决定，本技能提供步骤。放在会话最先读到的地方，
不要在它下面复述技能内容——副本会变成过期第二来源。

- **还没有约定**：写出仓库应有的那份，单独一个提交，并在交接时报出该提交。只写仓库自己
  决定的部分：范围；基准分支、改动分支与 worktree 命名；提交粒度和信息格式；交接前的
  确切检查命令；如何收尾、清理什么；容易出错的边界（不能碰的文件、别人的分支、密钥）。
  保持一屏可读完，长流程用链接而不是内联。
- **已有约定**：只补缺失的部分——通常就是上面那行指针——不要重构别人的文件，不要重复
  技能的默认值。
- **先问再写**：仓库不是你的（克隆、要回馈上游的补丁、有维护者的共享仓库）、已有约定与
  本流程冲突、或用户不希望把指令写进这个仓库时。不会交给后续会话的草稿工作不需要写。

写完按“只有这份文件的会话”复读一遍：它应该能自己开分支、跑检查、收尾，而不用问“这是什么意思”。

### 交接前复核

说明改动在哪（worktree 路径与分支）、基准分支之后是什么样。交接前跑 `git diff --stat`
看范围、`git diff` 看内容、`git diff --check` 看空白错误、`git status --short --branch` 看
未跟踪文件。检查误入的文件、生成的噪声、密钥和无关改动，确认该提交的都提交了。

### 收尾

只有改动确实落地后（PR 已合并，或内容可验证已在基准分支里）才清理，按顺序：

```bash
# 1. worktree 脏意味着还有未提交工作：提交它，或明确决定丢弃。
git -C .worktrees/<name> status --short --branch
git worktree remove .worktrees/<name>   # 只有自己创建的构建产物才用 --force

# 2. squash 合并后分支提交仍在，git branch -d 会以 "not fully merged" 拒绝。
#    先证明合并后的内容已在基准分支，再删：
paths=$(git diff --name-only <base>...<branch>)   # 路径含空格时需要加引号
git diff --quiet <base> <branch> -- $paths && git branch -D <branch>
#    diff 非空，或 PR 是关闭而非合并：内容不在基准分支，保留分支并报告。

# 3. 只有你推送过、且仓库认为它是一次性分支时才删远端分支。
git push origin --delete <branch>
```

然后 `git worktree prune`，并在持有基准分支的 checkout 里更新它
（`git fetch origin && git merge --ff-only origin/<base>`）；被别的 worktree 占用时在那里更新。

绝不在内容尚不存在于别处时删分支；绝不 `--force` 删除可能包含别人工作的 worktree；
不清理不是自己创建的 worktree 或分支——报告它。

### 没有 remote

没有 `origin` 的仓库没有 fetch、push、删远端分支这些步骤。本地提交，在交接时写明分支，
未经明确要求不创建 remote、不发布。远端不可达时同样保留本地提交，把 push 报告为受阻，
不要改写历史。

### 草稿工作区

`~/.future/workspaces/...` 下的聊天/线程 workspace、临时目录和其他草稿位置都是可丢弃的。
不要在那里初始化仓库：历史会随目录一起消失。把仓库放在持久的项目目录里，或先问用户。

## 6. 长任务用 goal

需要跨会话继续、长期运行、维护持久待办，或用户明确说“继续做”时，用 `future-goal`。
创建前先查是否已有匹配的 goal，定义清楚的完成证据；普通的一次性修改留在当前会话。

## 7. 工具边界与交接

只用当前真正可用的工具，按当前 shell 正确引用路径；委派出去的任务要边界清晰、有证据，
监督会话仍对整合和独立验证负责。

收尾说清结果、改了哪些重要文件或行为、工作记录在哪（分支与提交，或 PR）、跑过哪些验证、
还剩什么限制或人工检查。简单任务从简，大改动要让人能判断风险。
